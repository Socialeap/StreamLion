## Minimal automatic refund operation

The signed-in purchase account page provides **Request full Core refund**, the exact UTC deadline and the original request receipt time. Account/Origin checks bind the request to its owner. Browser amounts, policy, subject and timestamps are ignored. One D1 request per order survives duplicate clicks and uncertain responses. An unpaid or other-account order cannot initiate a request. A paid order awaiting business-tax review can still request its refund.

The purchase ledger snapshots the offer and 14-day period. `paid_at` comes from a signature-verified `payment_intent.succeeded` event, checked against the currently verified payment. Checkout creation, a success URL and mutable ledger update times cannot start the clock. If the timestamp arrives late, the request waits durably; it is not rejected because processing is late.

The small `streamlion-core-refunds` Worker checks up to 10 due requests every five minutes. The account page only records requests; the Worker alone receives a restricted refund-write credential. A conditional lease plus a stable Stripe idempotency key deduplicates processing. Before every retry it reads current refunds and discovers lost responses, including beyond Stripe's idempotency-key retention period. It refunds only the remaining gross payment after prior successful partial refunds. It will not create a second refund while another is pending. Unknown, disputed, mismatched or insufficiently verified payments fail closed.

Requested, pending, succeeded, failed and out-of-window states are separate. Actual succeeded Refund objects determine the successfully refunded amount; a pending/failed refund does not revoke paid access. Signed refund-created/updated/failed events and scheduled reconciliation preserve out-of-order safety. A verified full refund ends access from that order; unrelated paid orders and credit wallets remain separate. Provider failures, missing payment-time evidence and insufficient funds remain recorded and visible in the existing owner overview and customer request status. A known terminal Stripe failure requires resolution; the system does not repeatedly issue fresh refunds against an unresolved failure. There is no guarantee that software can refund unavailable funds.

No support-mail monitoring or owner awareness is needed to initiate an eligible in-app request. Existing support email remains an exception/help route; a timely request received there must retain its original received timestamp and be honored without imposing an in-app-only forfeiture. Do not publish an unattended email route as the routine request channel. Funding/provider exceptions can still require the owner or Stripe support.

Google-owned files remain accessible in the customer's Google account. The purchase gate retains device-backup download after refund; refunding does not delete/disconnect accounts, customer files or app records. Existing privacy, support and financial-record retention obligations remain; no new automatic deletion or invented retention deadline is introduced.
