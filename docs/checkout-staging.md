# Checkout pause and owner QA

**HOLD — deploy only after review/merge and explicit release approval.** This change adds server-side checkout controls; it does not configure production, open sales, grant an entitlement, send mail or authorize a charge, refund or AI call. Preserve the current matching `test` payment/AI-credit modes and all existing pilot policies. No migration is required. StreamLion uses GitHub and Cloudflare for this release; no Lovable action is required.

## Controls and defaults

| Server-only setting | Accepted values / effect |
| --- | --- |
| `STREAMLION_CHECKOUT_MODE` | `open`: ordinary checkout subject to existing checks. `paused`: deny checkout for everyone. `owner_qa`: allow only an authenticated Google subject in the private list below. Unknown or empty values fail closed as paused. |
| `STREAMLION_CHECKOUT_QA_SUBJECTS` | In `owner_qa` only: JSON array of 1–10 exact opaque Google subject strings, each 1–255 ASCII letters/digits/underscore/hyphen, maximum raw length 4,096 characters. Missing, malformed, empty, email/domain/wildcard or oversized lists deny everyone. Store as an encrypted Cloudflare Pages Production secret; no values in Git, chat, screenshots or public configuration. |

If checkout mode is **absent**, it defaults to `open` only when `STREAMLION_PAYMENTS_MODE=test`, preserving the existing test pilot. Live and other modes default to `paused`. Explicit `open` never bypasses live payment approval, provider/catalog validation, authentication, CSRF/account checks, license eligibility, credit-sales readiness; AI spending retains its own budgets. QA is a checkout restriction, not an entitlement or spending approval. It does not alter payment/credit modes or D1 policy values.

Use the owner's exact Google `subject` from their authenticated existing `/api/google/session` or `/api/purchase/status` response, reviewed privately by the owner. Do not use an email, a Stripe account ID, a client-supplied account header, or a guessed Google ID. The session cookie resolves the authoritative server session; the existing Origin and account-header consistency checks still apply to POSTs. Expired/missing sessions grant no QA access. Do not add a new login route, shared bypass token or public query-string override.

The gate applies to both `/api/purchase/checkout` and `/api/credits/checkout`, **before provider preflight, order mutation or reuse of a pending Checkout URL**. A denied authenticated request returns HTTP 403 with `code=checkout_paused` and no URL. Anonymous checkout still requires sign-in. Core/credit config returns `checkoutMode` and an account-specific `enabled` boolean; the credit boolean also requires its independent sales readiness. QA identities never appear in public responses, and catalog caching never caches authorization.

The public landing never presents a purchase offer during `owner_qa`, even for an authenticated QA owner. The direct purchase/credit page permits approved QA checkout, shows a QA notice (including that live checkout uses real money), and retains Google sign-in/restoration links while sales are paused. Existing license status and buyer workspace access are independent of this gate. Never interpret the presence of a QA checkout button as approval to make a real payment.

## Reconciliation boundary

Do not apply this gate to `/api/purchase/confirm`, `/api/credits/confirm`, status, signed webhooks, reconciliation or existing entitlements. The Core return page confirms an existing payment even when new sales are paused or the price quote is unavailable; verified buyers can still reopen the workspace. Credit confirmation and signed payment/refund/dispute processing continue when the checkout mode is paused or the QA list is malformed/changed. Preserve live credentials, modes, webhook endpoints, journals and the Google token encryption key after live payments exist.

This gate does **not** expire a Checkout Session already issued by Stripe, cancel a processing payment, revoke a completed purchase or stop an in-flight request that passed on an older deployment. After an authorized pause, separately identify and expire only open/unpaid StreamLion sessions if required, then reconcile processing/paid sessions. No such provider mutation is authorized by this change.

## Review and deployment gates

1. **Code/review:** record the exact reviewed commit and merged `main` SHA before deployment. This PR changes Pages Functions plus frontend; no D1 migration, Stripe object, auxiliary Worker or cron change is required. No `wrangler.jsonc` mode, budget, flag or secret value changes are included. The PR preview must not receive production D1 or credentials.
2. **Cloudflare activation:** after explicit approval, deploy only that approved Pages/Functions SHA through the existing pipeline. Leaving both new settings absent preserves the test pilot. To exercise a restriction later, the owner saves the exact approved mode/list in Production server settings and activates them on an approved deployment. Check the deployment's effective configuration, not just pending dashboard values. Do not add a production `open` default to Wrangler.
3. **Future live staging:** only after the separate Stripe/D1/email/entitlement plan is approved, deploy a complete matching live configuration with `STREAMLION_CHECKOUT_MODE=paused` or `owner_qa`. Preserve AI cost approval false, live paid-AI policy inactive/zero and both credit-sales switches false until separately approved. Coordination-only top-ups can later use `STREAMLION_COORDINATION_CREDIT_SALES_ENABLED=true` with verified coordination readiness, without AI approval; see [the separate plan](coordination-credit-topups-release.md). Owner QA cannot override those independent gates. Both credit and payment modes must match; the coordination relay must also match Pages. The checkout gate does not keep the Resend pilot allowlist active when payment mode becomes live.
4. **Frontend verification:** verify the same SHA on `/release.json`; anonymous/non-owner landing and purchase/credit pages must show no checkout offer/button. In QA mode the approved authenticated owner can see checkout eligibility on the direct page. Physical Android/PWA acceptance is separate from local component tests.
5. **Non-spending acceptance:** use synthetic local Stripe responses and signed events, or public config/status GETs only. Do not create a live Checkout Session, submit a card, send an email, or invoke AI without separate authorization and its exact allowance. Public config GETs can update ordinary D1 rate-limit/session-expiry counters; they do not charge a card or execute AI.
6. **Public opening:** separate explicit owner authorization is required to set checkout mode `open`, deploy it and verify effective public sales. Existing payment approvals alone no longer open checkout when the live checkout setting is absent. Credit sales also require their own readiness and sales flag.

The current `verify-purchases.mjs` and `verify-credits.mjs` scripts require `enabled:true`; they are open-sales checks, not closed-staging checks. For a paused deployment, inspect config directly: HTTP 200, correct catalog/mode, `checkoutMode=paused`, `enabled:false`. For owner QA, anonymous/non-owner config must be disabled; the owner's Core config may be enabled, and credit config is enabled only if credit readiness also passes. Test direct denied POSTs only with synthetic local fixtures until production QA is separately authorized. Signed webhooks must retain normal signature/mode/account/product verification and replay behavior in every checkout state.

## Pause and rollback

To pause **new** Core/credit checkout later, owner-authorized `STREAMLION_CHECKOUT_MODE=paused` plus an approved deployment keeps status/confirmation/webhooks alive. To remove one QA account, update the private list and activate the approved settings; an empty/malformed list closes QA rather than opening sales. Keep the underlying modes and live secrets in place. Both credit-sales switches false (or checkout paused) stop new top-ups; paid-credit policy inactive independently stops AI spending. Do not return paid AI to `disabled` or live payments to test as a rollback.

Before any code rollback to a version without this gate, review its consequence: that version can reopen Core checkout with a valid live bundle. Do not rely on a new setting an old build does not consume. Use the documented provider price/session pause under separate authorization if a compatible code rollback cannot retain the gate. Never delete locks, orders, wallet entries or webhook receipts to recover a release.

Required receipt: approved SHA and deployment ID; schema unchanged/no migration; secret names/type/presence only; effective checkout/payment/credit modes; anonymous/non-owner and owner eligibility checks; unchanged AI/email/pilot policy and writer lock; signed webhook/confirmation/replay results; separate frontend and owner/device QA results; any real payment/refund allowance and result if later authorized. Do not declare live QA or launch complete from local tests or merge alone.
