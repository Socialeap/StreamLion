# PWA alerts and Resend — gated implementation

StreamLion now has an integrated transactional Resend sender and optional Web Push. No Telegram or WhatsApp connector is required. Project records and revisions remain in the provider's Google workbook/Drive. This document is an activation procedure, not authorization to deploy, create credentials, send real messages, buy a plan or enable paid coordination.

The owner-approved restricted email pilot is documented in [coordination-pilot-activation.md](coordination-pilot-activation.md). Its [October 7 QA receipt and guarded push preparation](coordination-pilot-qa-2026-10-07.md) records live evidence and the next activation gates. Wrangler prepares coordination/email and optional push flags as true; the D1 test policy stays inactive until credentials, deployment and safe health checks pass. Push also requires valid matching VAPID settings and explicit device opt-in. Use those pilot procedures for current activation; the migration steps below remain the exact schema preparation procedure.

## User experience

- Invitations and renewed email access use the existing deliberate verification button and 20-minute, single-use fragment token. No private project information appears before verification.
- The Updates panel shows the latest 20 authorized project events. The server returns at most 100, with provider-private attachments omitted from client history. Notification acceptance is not client acknowledgment or approval.
- Optional device alerts are enabled from an explicit tap after authentication. Declining permission leaves the portal usable. iPhone/iPad clients first add the project to the Home Screen. Existing installations must accept the app update before subscribing.
- Routine edits wait 60 seconds and coalesce before email dispatch. When a corresponding push service has accepted an alert for a still-authorized subscription, routine email is suppressed. Acceptance cannot prove the device displayed the alert. Invitations, questions, approval requests, unacknowledged operational changes, delivery, closure and archive reminders retain email. Important non-invitation events can also receive push.
- Push text is neutral and contains no name, address, scope, price or access code. Tapping it opens the current authenticated portal. A stale or revoked grant must reverify; receiving a notification grants no access.
- Three devices per subscription owner are permitted. The pilot supports one role/client project per browser push subscription on this origin; switching requires turning off the previous subscription. Client subscriptions expire with their seven-day grant or earlier job deadline. Provider subscriptions expire within 90 days or earlier connection expiry. Reverify/re-enable after expiry. Multi-project client identity and consolidated device subscriptions are subsequent work.

## Required configuration

Configure the existing authorized Google/D1, purchase mode and credit mode in Cloudflare Pages Functions. The dedicated coordination Worker is a signed cron relay: it has only the coordination flag, matching payment mode, fixed HTTPS Pages origin and a separate scheduler signing key. Google, Resend and optional VAPID credentials remain in Pages; the relay has no D1 binding. `0009`, `0010` and `0011` must be present before coordination becomes available. Follow [backend-efficiency.md](backend-efficiency.md) for the additional exact preflight and runtime defaults. The existing `COORDINATION_MAILER` binding is a synthetic **test-mode compatibility transport only**; production uses Resend directly.

`COORDINATION_SCHEDULER_KEY` is a separate random 32-byte hexadecimal secret in Pages and the relay Worker. `COORDINATION_SCHEDULER_ORIGIN` is the relay's fixed HTTPS Pages origin; its payment mode must match Pages. This signing credential requires explicit owner approval and authorizes only the bounded maintenance callback. No Google, Resend or VAPID credential needs duplicating into the relay.

The API key alone does not establish delivery readiness: the sending domain/address, approved limits and signed webhook also require configuration. Disable click/open tracking for transactional mail in the Resend domain settings, and verify invitation links retain their original fragment. Messages are plain text and contain minimal instructions plus the portal/access link. No marketing, attachment or full-brief sender is implemented. Review the privacy changes before frontend publication.

For owner-operated VAPID generation, `node scripts/generate-notification-keys.mjs /absolute/private/path/streamlion-vapid.json` writes a new private file with mode 0600 and prints only the public key. It refuses an existing target. Put the private value directly in Cloudflare secret configuration; protect/remove the local file according to the owner's credential policy. Do not run this inside the repository or rotate an active key without a reviewed subscription transition.

## Delivery and cost controls

Every accepted coordination POST schedules a bounded dispatch of up to four messages per channel through `waitUntil`. A dedicated one-minute cron calls the signed Pages maintenance endpoint, which retries up to 20 per channel and performs existing coordination/archive maintenance using Pages' existing credentials. Replay and minute-slot claims precede that work. A durable global lock serializes delivery for this D1 database; each invocation stops beginning new attempts after 20 seconds. Each network attempt has a ten-second timeout. The cron is a fallback, not a delivery deadline guarantee. This is a bounded pilot; throughput and queue age need measurement before a larger rollout.

Daily and UTC calendar-month counters cap **send attempts**, conservatively counting retries as well as successes. Set limits within the owner-approved Resend allowance and account for any other apps using that account. Budget exhaustion retains queued messages; it never upgrades a plan or starts automatic recharge. Source flags alone cannot send: runtime readiness and the active policy are also required. Google/Cloudflare operation costs and any separately activated Resend plan still apply.

Resend receives one stable `Idempotency-Key` per durable notice. Its documented retention is 24 hours; StreamLion stops uncertain retries at 23 hours after the first attempt. Up to ten email attempts and five push attempts use exponential backoff. A ten-failure, bounced, complained, failed or uncertain email appears in the provider's review count. Never change a notice's identity to blindly resend an uncertain invitation: inspect the Resend receipt and original challenge expiry first. Native sends are paced at 600 ms intervals within each batch. External users of the same Resend account can still consume its rate limits; HTTP failures remain queued.

`accepted` means the send API accepted the message. Only a fresh, verified raw-body Svix signature can produce `delivered`, `bounced`, `complained` or `failed`. Duplicate events are idempotent. Minimal webhook metadata survives the race where delivery arrives before the send response. Complaints/bounces/failures take precedence over a later delivery event. None of these states proves reading, payment or approval. Push service acceptance is likewise not a read receipt.

Dispatch rechecks the paid account, payment mode, connection expiry/revocation, job archival/access deadline and client push grant. Expired invitation challenges are skipped. Arbitrary push hosts, credentials in endpoint URLs and redirects are rejected; only the supported Apple, Google, Mozilla and Windows push service hosts are allowed. Endpoint/key and queued contact data are encrypted with the existing approved Google encryption key; browser endpoints and private VAPID/Resend keys are never logged or returned by settings reads. Successful/skipped mail payloads are replaced with minimal encrypted receipts. Push metadata expires or is removed on logout/unsubscribe, and maintenance clears expired subscriptions, old push queue rows, seven-day webhook metadata and old budget counters. Resend's own email/log retention follows the owner's account and vendor policy.
